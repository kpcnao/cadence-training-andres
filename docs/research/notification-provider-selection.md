# Cadence in-app notification provider selection

**Recommendation: use Knock's hosted service, with a custom headless React inbox and Cadence-owned delivery/deduplication state.** This is an evidence-led selection, not a continuation of historical Knock usage. Courier is the runner-up.

**Source retrieval date: 2026-11-13.** Only official documentation, pricing, API references, and published npm package manifests were used for provider claims. “Verified” below means documented by the cited primary source, not exercised in a provider account. **Unknown** means the reviewed official material did not establish the capability; it does not prove absence. No sign-up, provider write, or runtime integration test was performed.

## Cadence requirements being evaluated

The [catalog decision](https://github.com/kpcnao/cadence-training-andres/issues/3) defines eight persistent, recipient-specific kinds:

| Kind | Recipient at event time |
| --- | --- |
| Discussion Question | The course Instructor, except self-notification |
| Discussion Reply | The question author, except self-replies |
| Seat Claimed | The Team Admin who bought the Team Licence |
| Refund Request Opened | The buyer and every Platform Admin |
| Refund Request Approved | The buyer |
| Refund Request Declined | The buyer |
| Issued Refund | The buyer |
| Failed Refund | The buyer |

Each source event must produce at most one Notification per recipient, including after retries. The [inbox decision](https://github.com/kpcnao/cadence-training-andres/issues/4) requires a custom bell popover/mobile panel, persistent per-user history, real-time updates, unread badge counts, All/Unread filters, read and unread toggles, mark-all-read, and 20 initial items with explicit “Show older” pagination. Provider failures must not roll back domain writes or masquerade as an empty inbox. Preferences, archive, deletion, retention, integration, and restoration policies remain later decisions.

## Decision and rationale

Knock has the best overall fit for Cadence's stated requirements:

- **Persistent history:** in-app `FeedItem` data is documented as available indefinitely, unlike Novu's 30-day Free/90-day paid inbox retention. Archive is reversible, and whole-user deletion includes messages.[^lifecycle]
- **Eight catalog kinds without a Free-plan workflow cap:** Free includes unlimited workflows and 10,000 delivered messages/month. Each discussion, Seat-claim, or refund-outcome kind can have a stable workflow key, typed data, and a deep link; filtering can use workflow source, categories, or trigger data.[^catalog]
- **Cadence-owned visual design:** React hooks expose real-time items, unread counts, read/unread, mark-all-read, archive, and cursor pagination (`page_size: 20`, `fetchNextPage()`). A custom bell and popover are also available without accepting the stock UI.[^ui][^actions]
- **Production browser security:** enhanced security requires a backend-signed RS256 user JWT; expiry and explicit resource grants are supported.[^auth]
- **Explicit React 19 package compatibility and generated TypeScript workflow types.** Next.js and TanStack Router peers are optional, so they do not force a router change.[^react][^server]
- **A usable export path:** paginated Messages APIs expose engagement/archive state, with rendered content available separately; per-user feed export is also possible. Courier's list endpoint omits content and explicit read/archive state, making its exit story weaker.[^export]

The choice is conditional on two design rules. First, Knock's trigger idempotency lasts only 24 hours, so it cannot be Cadence's dedupe system of record. Second, indefinite feed retention is not a deletion policy: archive is not erasure, and no individual-message permanent-delete endpoint was found. Whole-user deletion is documented. These limitations are acceptable for the current “decide lifecycle later” requirement, but selective erasure or fixed feed-retention windows would be a launch-blocking proof point.[^dedupe][^lifecycle]

### Delivery guarantees remain Cadence-owned

Provider triggers cannot make a Cadence domain commit and provider call atomic. Ticket #6 must decide the integration mechanism; a durable outbox is the baseline to evaluate. It would persist the catalog kind and a unique `(domain_event_id, recipient_id)` before calling the provider, reuse a deterministic provider idempotency key on retry, and trigger each recipient separately. Provider key windows cover transport retries; the database uniqueness rule prevents duplicates after those windows or after an application redeploy. Track provider message/run IDs, attempts, and terminal failure for reconciliation. A WebSocket event should trigger/reconcile the durable feed, not be treated as the sole delivery mechanism.

No reviewed provider offered a React Router 8-specific integration guide. The verified-compatible pattern is framework-neutral: call the server SDK from a Cadence server action/route, expose a session-backed token endpoint, and mount the client SDK only in the browser. A small Cadence smoke test remains required for SSR/hydration, Strict Mode, socket teardown, token refresh, and the custom popover. SuprSend's older package must not be selected from stale examples.[^ui]

| **MagicBell** | **Weakest volume allowance:** 1,000 deliveries/month, but all channels/features and unlimited users/team. One user/channel is one delivery. | Startup **$249/month**, 50,000 deliveries, then **$0.0025/delivery**. |
| **SuprSend** | 10,000 notifications/month, unlimited channels/team; feed carries SuprSend branding. User preferences are not in Free/Essentials according to the plan comparison. | Essentials **$100/month billed annually**, 50,000 notifications, then **$2/1,000**. All five hosted options remove feed database and WebSocket operations. All still require Cadence to own recipient mapping, server secrets and token minting, templates, delivery/retry state, monitoring, and lifecycle policy. Courier requires manual JWT refresh; Knock and SuprSend document refresh callbacks. Novu self-hosting is a portability option, not an operational shortcut: its production topology includes API, Worker, WebSocket, Dashboard, MongoDB, Redis, and object storage, with some cloud-only feature differences.[^ops]

## Migration, export, and provider-held state

Current `main` has no in-app feed or provider integration ([inventory decision](https://github.com/kpcnao/cadence-training-andres/issues/2)). This is therefore a new integration, not evidence that historical hosted Knock data survives or must be restored; clean start versus restoration remains ticket #8's decision.

**Verified export mechanisms are not equivalent to lossless migration.** No reviewed provider documented a general historical-feed import preserving original IDs/timestamps and read/unread/archive state. Template recreation, recipient/preference migration, token/SDK replacement, and a backfill or read-only legacy-feed strategy must be planned separately. Do not promise exact historical-state restoration without a provider-specific proof.[^export]

| Provider | Verified extraction path and principal limitation |
|---|---|
| **Knock** | Paginate `GET /v1/messages` with engagement/archive timestamps, then fetch rendered content separately; or enumerate users and cursor through each feed. Feed items survive log expiry, but ordinary message logs last 30 days (90 Enterprise). Warehouse export is Enterprise. No bulk import found. |
| **Novu** | `GET /v1/messages` supports subscriber/channel filters and returns content plus read/seen state. Export within 30/90-day retention. Self-hosting offers direct data control and the same API shape, but no one-click cloud-to-self-host migration was found. |
| **Courier** | `GET /messages` provides IDs, recipient/template, delivery status, and timestamps, but its documented response omits rendered content and explicit read/archive state. That is a material exit-risk gap to resolve. Feed persists until archive/expiry. |
| **MagicBell** | Per-user notification list/fetch supports status/category/topic filters and cursor pagination. No dedicated bulk export, fixed retention policy, or full-state import was verified. |
| **SuprSend** | **Strongest documented export record:** `GET /v1/message/` can include rendered content and read/archive timestamps/status with recipient/workflow/time filters. Content inclusion lowers maximum page size to 20. No historical-state import was found. |

To keep a future switch practical, Cadence should retain its canonical domain-event record, catalog kind, recipient, rendered-input data, deep link, dedupe key, and provider IDs independently of the vendor. Preferences and retention/deletion decisions also need a portable representation. Export provider state periodically where feasible. During migration, prefer a cutover plus read-only legacy history or a verified backfill; do not dual-send indefinitely, because that creates another deduplication problem.

## Runner-up and tradeoffs

**Courier is the runner-up.** Select it instead if multi-channel pricing, up-to-one-year idempotency, and long provider retry/failover windows outweigh exit and lifecycle unknowns. Its pay-as-you-go Business plan also avoids Knock's $250 step. Before choosing it, require evidence for complete feed-content/read/archive export and permanent user/inbox erasure, and accept the manual token-refresh burden.[^dedupe][^retry][^export][^auth]

The other candidates remain credible but are weaker defaults for this ticket:

- **Novu:** best open-source/self-host control and lowest paid entry; strong React APIs and permanent notification deletion. Free's five-workflow cap, hard 10,000-run stop, 30-day inbox retention, support-enabled idempotency, and lack of a general delivery re-drive make it less suitable for eight independent catalog kinds and persistent financial history.[^pricing][^lifecycle][^retry]
- **SuprSend:** best export primitive, 20-item default feed, short-lived scoped JWTs, and lower entry paid price. However, preferences require Business according to pricing, default feed retention and managed in-app recovery were not established, and fully headless unread-badge semantics are less clear.[^pricing][^export]
- **MagicBell:** capable feed/UI primitives and simple custom-headless UserClient. Its 1,000-delivery Free allowance is small; React 19 runtime compatibility, automatic recovery, retention, and idempotent broadcast creation were not verified.[^pricing][^react][^dedupe]

## Unknowns / acceptance gates before implementation

1. **Runtime:** install/test only in a disposable Cadence proof of concept: React 19.2 + React Router 8 SSR/hydration, custom bell, real-time reconnect, 20-item older-page loading, read ↔ unread, mark-all-read, and token expiry. Package ranges alone are insufficient.
2. **Exactly-once behavior:** failure-inject the outbox around request timeout, 409/429/5xx, duplicate domain events, and retries after 24 hours. Verify one feed item per domain event/recipient.
3. **Privacy/lifecycle:** verify the required per-item erasure and retention policy, data-region/DPA/subprocessor terms, logout/token revocation, and cross-tab behavior. This research verifies API authentication controls, not a legal/privacy review.
4. **Exit drill:** export a representative populated feed and assess content, deep links, preferences, and engagement-state fidelity before production lock-in.
5. **Commercial:** re-check pricing/limits at purchase time. Model actual monthly recipients concurrently with possible future email/push, because “message,” “run,” “send,” and “notification” have materially different billing meanings.
